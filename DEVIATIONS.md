# Deliberate deviations

Every place this library knowingly differs from the Go implementation
(citius-core / citius-server) or from the C stub in citius-c-api, with the
reason. Anything that differs and is not listed here is a bug.

## From the Go implementation

| # | Go | Here | Why |
|---|---|---|---|
| G1 | Orchestrators, repositories and the policy engine are built per request by factories. | Built once per `agc_ctx`, shared through `Arc`; the context is used concurrently. | A library has no requests; the deck's verdict (slides 36, 41). Go's per-request repository lock serialised nothing. |
| G2 | One error type maps to gRPC status in `ToStatusError`; `errors` imports gRPC codes. | `domain::core::Error` knows no transport; `ffi/error.rs` alone maps to `agc_rc`. | Keeps the domain free of the C boundary, as Go intends but does not achieve. |
| G3 | Domain `Code` has 14 values; several C-distinct cases share one. | `Code` is as fine as the C error set needs, e.g. `NoMatchingTemplate` vs `TemplateNotFound`. | The C API reports these separately. |
| G4 | `template.Registry.Select` documents "first matching active template" but does not filter by status. | Only `ACTIVE` and `ACCEPTABLE` templates are selected. Naming a single deprecated or forbidden template that would serve the intent fails with `TemplateDeprecated` / `TemplateForbidden`. | Implements the documented contract, and the C API has the specific codes. |
| G5 | `MatchesScope` re-parses a template's scoped capabilities on every call and fails the request if one is malformed. | Capabilities are parsed once when the template is created; a malformed catalog fails to load. | A catalog error is a configuration error, found at startup. |
| G6 | The zero `ScopeSpecification` matches every template, across kinds. | A scope's `UNSPECIFIED` value matches any scope of that kind only. | The C API always names a kind (`AGC_SCOPE_KIND_NONE` is rejected). |
| G7 | Domain types embed generated protos (`key.Key` wraps `storepb.Key`). | `Template` wraps the API `TemplateInfo` as Go does; scope and key types are plain Rust types that convert from protos at the edge. | Unknown enum values are rejected once, on the way in, instead of travelling as `i32`. |
| G8 | An empty policy name skips policy evaluation entirely. | There is no bypass: every call names a policy, or `agc_ctx_config.default_policy` supplies one; with neither the call is `AGC_ERR_INVALID_ARGUMENT`. | A library must fail closed; the C API marks `policy_name` required. |
| G9 | Rules sections that are not evaluated (`allowed_scopes`, `allowed_providers`, `key_configuration`, `allowed_transformations`, `allowed_migrations`, `keyless_operations`, `min_nist_status`) are accepted and ignored. `quantum_safe` and `min_security_strength_bits` are parsed but not evaluated. | The unevaluated sections are rejected when the policy is written. `quantum_safe` and `min_security_strength_bits` are evaluated against the template's security properties. | A policy author must never believe a rule is enforced when it is not. |
| G10 | The rules JSON is re-parsed on every evaluation, through a pluggable `RulesEvaluator`. | Rules are parsed and validated once, when the policy is written, and stored parsed. There is no strategy trait yet. | One rules language exists; a trait for a second one is easy to add when it does. |
| G11 | `Enforcer.CreatePolicy` checks for an existing name, then puts. | The repository's `create` and `update` are atomic. | Two concurrent creates of one name could both succeed. |
| G12 | citius-core's `Enforcer.DeletePolicy` deletes regardless of keys, and citius-server does not expose it (the DeleteCryptoPolicy handler is a stub). | `agc_delete_policy` is implemented. It fails with `AGC_ERR_CRYPTO_POLICY_VIOLATION` while keys are bound to the policy (an application-layer check). | Kept although the server stubs it (see G30): the core implements it and agc_policy.h requires it. Deleting a policy that keys still name would leave those keys unusable. The error code follows the C stub. |
| G13 | The provider contract uses the `caas.provider.v1` messages (`providerpb`) for wire identity with remote providers. | `provider::Backend` takes and returns Rust types. | Providers here are in process; an adapter for a remote provider would translate. |
| G14 | The stored key material is the serialized `GenerateKeyResponse`. | A small versioned format of the private bytes, the public bytes and their encodings (`GeneratedKey::to_bytes`). | No `providerpb` (G13). The encodings match Go's software provider: SEC1 or PKCS#8 private keys, SPKI or raw public keys. |
| G15 | Provider matching fails with `ProviderNotFound` (or `FailedPrecondition` for a pinned provider's unmet requirements). | `ProviderNotFound` (unknown name), `ProviderIncompatible` (a pinned provider that does not serve the template), `NoMatchingProvider` (requirements unmet). When templates match the intent but no provider qualifies, creation reports `NoMatchingProvider`, not "no template". | The C API has the specific codes; the caller learns which half to change. |
| G16 | The software provider serves RSA-PSS and RSA PKCS#1 v1.5. | The rustcrypto provider does not. | The RustCrypto `rsa` crate has an open timing side channel (RUSTSEC-2023-0071). |
| G17 | The software provider reports implementation properties freely. | rustcrypto claims only memory safety: no FIPS validation, audit, constant-time or CVE claims. | A provider must not claim what an audit would contradict (Go's own rule). |
| G18 | Repositories are built per request with their own lock, so a read-modify-write of a key by two requests can lose one change. | `KeyRepository::update` is optimistic: it stores a key only at the revision it was read at, else `AGC_ERR_CRYPTO_CONCURRENT_ACCESS`. | Lost updates to key versions are not acceptable; the C API has the code. |
| G19 | `CreateKey` stores the key, then the response is built. | The response size is checked against the caller's region after the key is generated and before it is stored; a region too small creates nothing and reports the exact size needed. | The STORAGE CONTRACT for create operations (agc_key_types.h). |
| G20 | `KeyMetadata` (the read model) is assembled from the key and its version, both of which carry material. | `app::KeyMetadata` carries no private material; listings and iterators hold only metadata. | Secrets should not travel further than the operation that needs them. |
| G21 | Material compatibility requires each template's declared `key_material_family` and cross-checks it against the typed algorithm. | The profile is derived from the typed algorithm alone, with Go's shape rules. | The pinned API version predates `key_material_family`; the cross-check returns with a newer pin. |
| G22 | `TransformKey` requires a scope specification. | Without one, the current version's applies; "any scope of the kind" means the key's own scope. Either way the scope cannot change (`AGC_ERR_CRYPTO_INCOMPATIBLE_PARAMETERS`, Go: FailedPrecondition). Kept material without the approved lineage a policy requires is a `POLICY_VIOLATION`. | A transform cannot change the scope, so asking the caller to repeat it adds nothing. |
| G23 | Migration errors are `FailedPrecondition` or `ProviderNotFound`. | A strategy that cannot be carried out is `AGC_ERR_CRYPTO_MIGRATION_NOT_FEASIBLE`; material that may not leave its provider is `AGC_ERR_CRYPTO_KEY_NOT_EXTRACTABLE`. Changing the algorithm during a migration, and target provider configuration, are `AGC_ERR_NOT_IMPLEMENTED` (Go: InvalidArgument). | The C API has the specific codes; "not implemented" says the request is understood but not offered. |
| G24 | `ValidateMigration` needs exactly one target. | `AGC_VALIDATE_MIGRATE_TARGET_ANY` (legal in the proto) assesses every other provider. A TRANSFORM intent is assessed by the same checks as `agc_transform_key`, with no side effect; `prefer_retain_bytes` is a preference, so a transform that cannot keep the material but can regenerate it is feasible and the recommendation says so. `complexity_level` is 0 ("not assessed"): the proto's 1-5 scale has nothing behind it, and Go does not set it. | The C API offers these; inventing a complexity score would mislead. |
| G25 | `TransformKey` and `ValidateMigration` share checks with the operations they assess only partly. | Transform is planned (every check, no material generated) and then executed; its pre-flight runs exactly the plan. | A pre-flight that runs different checks from the operation is wrong exactly when it matters. |
| G26 | Only signature operations check that the template declares the operation for the version's scope. | Every keyed operation checks it (`AGC_ERR_CRYPTO_KEY_OPERATION_NOT_ALLOWED` otherwise). | One rule; the catalog declares operations for every template. |
| G27 | Decrypt returns whatever output the provider reports. | A decryption's metadata carries the version used, the "no output" kind and the request's user context; the provider's decrypt has no system parameters to report. A CBC padding error is `INVALID_ARGUMENT` with a generic message. | Decryption generates nothing; CBC is unauthenticated, so its errors must not tell an attacker more than "this does not decrypt". |
| G28 | A prehashed scope spec carries `accepted_digest_hashes`. The template offers the list; each key version records it, optionally narrowed at creation. DigestSign refuses any other hash with `InvalidArgument` and returns the hash in `OperationMetadata.digest_hash`, from which DigestVerify takes it. The provider checks the digest length for fixed-length hashes only. | The pinned API (headers and descriptor) has neither field. The accepted list is the template's, held by the provider with Go's catalog values: ECDSA P-256 SHA-256/384/512, P-384 SHA-384/512, P-521 SHA-512, Ed25519ph SHA-512. It cannot be narrowed per key. DigestVerify takes the hash from the request (`agc_digest_verify_request.hash_algorithm`). Every refusal is `INVALID_ARGUMENT`, as in Go. The core checks the length for every provider, and a hash without a fixed length is refused. | Pin lag. The C contract has no place to record or return the list. agc_digest_sign_request relies on the length check to stop a SHA-1 digest passing as SHA-256. When the pin includes the fields, record the list per version as Go does. |
| G29 | Ed25519 verification is `crypto/ed25519.Verify`, which accepts signatures with small-order points. | Verification is strict (`verify_strict`, `verify_prehashed_strict`): small-order points and non-canonical encodings are invalid. | The catalog claims `nonMalleable` and SUF-CMA for Ed25519, which only strict verification gives. Honest signatures verify the same in both. |
| G30 | Where the server only stubs an RPC, the operation is unavailable. | The C function exists and returns `AGC_ERR_NOT_IMPLEMENTED` with a last_error message, as the stubbed handler returns `Unimplemented`. Exceptions: `agc_delete_policy` (G12) and `agc_list_policies`, whose server handlers are stubs but which citius-core's `Enforcer` implements; both are exposed. | Follow Go: behaviour Go has not defined is not invented here. The symbol is still exported, so C programs link and can detect the gap at run time. |
| G31 | `core.Scope` lists 28 scopes in a fixed order with fixed names (`signature_standard`, ...). It has no asymmetric-encryption scope, so a spec with one fails `ScopeSpecificationFromProto` with `InvalidArgument`. | The same list, order and names (`Scope::ALL`, `Scope::name`). `AGC_SCOPE_KIND_ASYMMETRIC_ENCRYPTION`, which agc_scope.h marks reserved, and the proto's asymmetric-encryption family are refused with `INVALID_ARGUMENT` wherever they enter. | Not a deviation from Go. It is recorded because the proto defines the kind. |
| G32 | `instanceInfo` never sets `ProviderInstance.enabled`, so every instance it reports reads as disabled, although its comment says every served instance is enabled. | `enabled = 1` for every instance. | A caller filtering on `enabled` would otherwise discard every instance. Everything else in the provider records is as Go fills it, including the unset `provider_type` and the `enabled = 0` on template support. |

## From the C stub (citius-c-api/src)

| # | Stub | Here | Why |
|---|---|---|---|
| C1 | `agc_rc_message` returns "unknown result code" for every `AGC_ERR_CRYPTO_*` code. | Crypto codes get their name in words, e.g. "key not found". | A defined code is not unknown. Local codes keep the header's text. |
| C2 | A panic does not exist in C. | A panic inside any export is caught and returned as `AGC_ERR_INTERNAL`; state behind a lock it poisoned fails closed from then on. | Never unwind into C, never abort the host. |
| C3 | `agc_secure_alloc` is `malloc` + best-effort `mlock`; `agc_secure_free` zeroes `n` bytes and `munlock`s. | Each allocation is its own page-aligned anonymous mapping: locked (best effort), excluded from core dumps on Linux, the whole mapping zeroed and unmapped on free regardless of `n`. | `munlock` on a malloc'd block unlocks every other secret sharing its pages, and freed heap pages are reused; trusting `n` could leave a secret's tail behind. |
| C4 | `require_locked_memory` is honoured by probing `mlock` at `agc_ctx_open`. | `agc_ctx_open` returns `AGC_ERR_NOT_IMPLEMENTED` for it until key material is held in locked memory. | Accepting the flag would promise a protection the library does not yet give. |
| C5 | The stub's metadata codec is hand-written per its header. | The same contract, with two clarifications. User-context map entries are accepted in any order under protobuf, because Go's encoder does not sort them; duplicate keys are rejected. Encoding sorts them, so output is deterministic. A vendor output arm is refused with `AGC_ERR_CRYPTO_PROVIDER_NOT_FOUND` when encoding as well as decoding, because no registered provider defines its layout. | Rejecting unsorted maps would refuse valid blobs from the Go service; an arm without a provider has no defined meaning. |
| C7 | agc_core.h allows `key_store_uri = "file:<directory>"`. | Every non-NULL `key_store_uri` is refused with `AGC_ERR_NOT_IMPLEMENTED`; keys are held in memory only. | A file store needs its at-rest protection agreed first: plaintext key material on disk is not offered. agc_ctx_open allows refusing a setting the build cannot honour. |
